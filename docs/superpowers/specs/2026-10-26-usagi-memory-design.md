# 우사기 1:1 대화 기억 (규칙 기반) — 설계

> 상태: 사용자 승인 · 2026-10-26
> 표시: **[사용자]** 사용자가 정한 것, **[판단]** 설계자가 정한 것(빌더가 더 나은 쪽으로 바꿀 수 있음), **[빌더]** 빌더에게 맡긴 것

## 1. 의도

`/우사기`로 만드는 1:1 비공개 스레드에서 우사기와 대화할 때 **진짜 대화하는 느낌**을 준다.

- 사용자가 말한 "대화스러운" 순간: 물으면 돌아오는 답이 **물음의 의도에 가까울 때**. 이어지는 물음이 앞과 같거나 비슷한 문맥일 수도, 아닐 수도 있는데, 그때도 **문맥에 맞춰 의도에 가장 가깝게** 답할 때 **[사용자]**
- 사람마다 기억을 쌓아 다음에 만났을 때도 이어 간다 **[사용자]**
- 모르는 물음은 그 사람이 "이런 뜻이야"라고 알려 주면 기억했다가 다음에 비슷한 물음이 오면 쓴다 **[사용자]**
- 까닭: 지금 우사기(`src/lunchbot/chat.py`)는 채팅을 한 번씩 따로 읽어 종류(인사, 음식, 슬픔 …)만 가르고, 직전 답만 기억한다(되풀이 안 하려고). 그래서 물음에 답하지도, 문맥을 잇지도 못한다
- AI(언어 모델) 없이 지금 구조(규칙 기반)로 만든다 **[사용자]**. 나중에 "채팅 읽기"만 AI로 바꿀 수 있게 의도·기억 데이터 모양을 디스코드·문장과 떼어 둔다 **[판단]**

## 2. 목표

- **G1 물음에 답하기:** 물음을 읽어 미리 정한 의도 중 가장 가까운 것을 고르고, 봇이 실제로 아는 정보(오늘 추천·투표 결과 등)로 답을 채운다
- **G2 짧은 문맥:** 화제 없이 짧게 묻는 말("그럼 저녁은?", "거기 어디야?", "왜?", "너는?")은 직전 화제·대상을 이어받고, 자기 화제가 분명하면 새 이야기로 바꾼다. 우사기가 가끔 되묻고 다음 채팅을 그 물음의 답으로 읽는다 ("배고파" → "뭐 먹고 싶어?" → "라멘" → "라멘 좋다!") **[판단: 되묻기는 처음 제안에 있었고 반대는 없었음]**
- **G3 긴 기억:** 사람마다 뽑아 둔 정보로 답할 때 기억을 꺼낸다 ("어제 라멘 먹었어?", "오늘은 좀 괜찮아?", "3일 만이네!"). 그 사람이 채팅했을 때만 답하고, 우사기가 먼저 메시지를 보내지는 않는다 **[판단]**
- **G4 가르치기:** 모르는 물음에 그 사람이 알려 준 뜻이나 답을 기억해서, 다음에 비슷한 물음에 쓴다
- **G5 유출 방지:** 개인 대화가 새어 나가지 않게 한다 (§5)
- **G6 등급:** `/우사기`(1:1 비공개 스레드)와 기억 기능을 같은 등급, **직장인 갑옷씨 이상**으로 둔다. 직장인 아래가 되면 1:1 스레드에서 내보낸다 (§8) **[사용자]**
- **G7 나간 사람 기록 지우기:** 서버를 나가거나 추방된 사람의 사람별 기록을 모두 지운다. 이미 나간 사람의 남은 기록도 찾아서 지운다 (§10) **[사용자]**

## 3. 하지 않을 것

- AI·언어 모델, 외부 정보 API (날씨 등) **[사용자]**
- 공개 우사기 채널의 답을 바꾸기. 물음 답하기·기억·가르치기는 **1:1 스레드에서만** 하고, 공개 채널은 지금처럼 답한다 **[사용자: "1:1 대화할 때"]**
- 디스코드에 올라간 스레드 메시지를 지우거나 숨기기 (§5.6). 단, 서버를 나가거나 추방된 사람의 1:1 스레드는 통째로 지운다 (§10)
- 우사기가 먼저 말 걸기 (정해진 시각에 보내는 메시지 등). 기억은 답할 때만 꺼낸다 **[판단]**
- `/우사기`로 스레드를 열 때의 인사(버튼 서버가 보냄)에 기억 넣기. 인사는 지금처럼 두고, 기억은 스레드 안의 답에서만 쓴다. 그래서 버튼 서버는 인사에 키가 필요 없다 **[판단]**
- 기억 끄기 스위치. 기억은 **항상 켜 둔다** **[사용자]**
- 시간이 지나면 기록을 자동으로 지우기. 기록을 지우는 경우는 §10의 두 가지(나가기, 추방)와 본인의 `/기억 지우기`뿐이다 **[사용자]**
- AWS 배포에서 동작하기. 이 기능은 **로컬 도커에서만** 동작하게 만든다 (2026-10-25 사용자 "우선 로컬 기준으로만", 지금 배포 없음). 배포하게 되면 키 보관(예: KMS)과 `/기억` 명령 처리 위치를 다시 설계한다

## 4. 실패로 보는 것

- A와의 대화에서 나온 **무엇이든**(기분, 좋아하는 것, 가르친 뜻·답, 짧은 문맥, 마지막 대화 날)이 B와의 대화나 공개 채널에 나오는 것 **[사용자]**
- 1:1 스레드 대화 원문이 파일·로그·백업·GitHub 어디에든 남는 것 **[사용자]**
- 저장된 기억을 운영자(사용자 본인 포함)가 파일을 여는 것만으로 읽을 수 있는 것 **[사용자]**
- 그 사람이 모르는 사이에 기록되는 것 (안내를 보기 전, 번역이 꺼져 되물음을 못 보는 동안) **[판단]**
- 모르는 물음에 아는 척 엉뚱하게 답하는 것 **[판단]**
- 우사기 소리 한 토막 = 하치와레 번역 한 토막 규칙이 깨지는 것 (기존 사용자 결정, `hachiware.Script`, `speak()`)

## 5. 유출 방지 (사용자가 다섯 가지 모두 맞다고 함)

목적은 **개인 대화가 유출되지 않게** 하는 것이다 **[사용자]**.

1. **원문은 저장하지 않는다.** 기억에 필요한 짧은 정보만 뽑아 저장한다 **[사용자]**. 예외는 가르치기(§7)에서 그 사람이 기억하라고 준 것(가르친 물음의 낱말, 알려 준 답 문장)뿐이고, 이것도 암호화한다
2. **참여자마다 다른 키로 암호화한다.** A의 키로는 B의 기록을 풀 수 없게 해서 섞이지 않음을 암호로도 지킨다. 키는 저장 폴더(`.local-s3/`), 코드, GitHub에 두지 않는다 **[사용자]**
3. **스레드 대화는 로그에 남기지 않는다.** 지금 `scripts/usagi_bot.py`는 `"{이름} 의 채팅 N개에 답함: {우사기 소리}"`와 `"하치와레: {번역 줄}"`을 스레드에서도 로그로 남기는데(번역 줄은 대화의 뜻을 드러냄), 스레드에서는 이런 로그를 끈다. 오류 로그에도 스레드 채팅 내용·이름을 넣지 않는다. 이 로그 끄기는 기억 기능을 쓰는 사람만이 아니라 **모든 1:1 스레드**에 적용한다 **[사용자: "1:1 비공개 스레드 내용은 어디에도 기록하지 말고"]**. 공개 채널 로그는 지금처럼 둔다 **[판단]**
4. **본인이 자기 기억을 보고 지울 수 있다** **[사용자]**. 명령은 직장인 갑옷씨 이상만 쓸 수 있으므로(§9), 직장인 아래로 강등된 사람은 기억이 남아 있어도 볼 수도 지울 수도 없다 (사용자가 이 결과를 알고 정함)
5. **미리 알린다.** 하치와레가 "무엇을 기억하는지, 암호화해서 저장한다는 것, 서버를 나가거나 추방되면 지운다는 것, `/기억 보기·지우기`로 언제든 보고 지울 수 있다는 것"을 알려 준다 (생일 안내와 같은 방식) **[사용자]**. 기억을 쓸 수 있는 사람(§8)이 1:1 스레드에서 처음 채팅할 때 알리고, 알리기 전에는 아무것도 기록하지 않는다. 이미 스레드가 있는 사람도 기능을 켠 뒤 처음 채팅할 때 알린다 **[판단]**
6. **막을 수 없는 것:** 디스코드의 비공개 스레드는 서버 주인과 '스레드 관리' 권한이 있는 사람이 디스코드에서 열어 볼 수 있다. 이 권한을 가진 사람을 최소로 두는 것이 대책이다 (사용자에게 알렸음)
7. **"운영자도 볼 수 없게"의 수준:** 봇이 기억으로 답하려면 풀어야 하고, 봇은 사용자 Mac에서 돈다. 그래서 목표는 "일부러 코드를 고치거나 키를 빼내지 않는 한 볼 수 없게"이다. 파일·백업·GitHub·도커 볼륨에는 암호문만 남는다 (사용자에게 알렸음)

### 5.1 키와 암호화 **[판단]**

- **마스터 키:** 우사기 봇이 처음 뜰 때 무작위로 만들어, 프로젝트 폴더·`.local-s3/`·`.env` 밖의 도커 named volume(예: `usagi-vault`)에 둔다. 어디에도 출력하지 않는다. 볼륨을 잃으면 기억도 모두 못 푼다 (기억은 없어도 되는 데이터라 받아들임)
- **사람 키:** `blake2b(key=마스터, data="memory:" + 서버 id + ":" + 사용자 id)` 로 만든다 (표준 라이브러리 `hashlib`)
- **암호화:** PyNaCl `SecretBox` (XSalsa20-Poly1305, 위조 감지). PyNaCl은 이미 도커 이미지에 있어 새 패키지가 필요 없다 (`docker/requirements.txt`)
- **파일 이름도 숨김:** 누가 우사기와 대화했는지도 드러나지 않게, 파일 이름을 `blake2b(key=마스터, data="name:" + 서버 id + ":" + 사용자 id)`의 16진수로 한다: `memories/{서버 id}/{해시}.json` = `{"v": 1, "box": "<base64 암호문>"}`
- 지금 `storage`는 JSON을 읽고 쓰므로 암호문은 base64로 JSON 안에 넣는다
- `/기억 보기`를 버튼 서버(`interaction` 컨테이너)가 처리하면 그 컨테이너도 같은 볼륨을 읽어야 한다 **[빌더: 명령을 어느 쪽이 처리할지]**

## 6. 대화 (물음 답하기와 문맥)

### 6.1 의도 후보 (사용자가 이 목록으로 하자고 함)

1. **봇이 아는 걸로 정확히 답하는 물음:** 오늘 점심 뭐야 / 정해졌어? / 어디 가? (투표 결과, 추천 5곳) · 저녁 추천 언제 와? / 지난번에 뭐 먹었지? (저녁 추천 시각, 최근 선택) · 내 생일 언제로 돼 있어? / 게임 점수 몇 점이야? / 내 등급 뭐야? · 지금 몇 시야? / 퇴근까지 얼마나 남았어? (시각 계산)
2. **우사기에 대한 물음** (정해 둔 설정으로): 너 누구야 / 뭐 좋아해 / 밥 먹었어? / 하치와레는 누구야?
3. **나에 대한 물음** (그 사람 기억으로): 나 기억해? / 내가 뭐 좋아한다고 했지? / 우리 마지막으로 언제 얘기했지?
4. **기분·잡담** (공감하거나 골라 주기): 심심해 뭐 하지? / 힘든데 어떡해? / 뭐 먹을까? (오늘 추천 5곳 중 하나를 골라 줌)
5. **이어지는 짧은 물음** (앞 문맥을 이어받음): 그럼 저녁은? / 거기 어디야? / 왜? / 너는? / 진짜?

봇이 아는 정보의 출처는 지금 저장소에 있다: 오늘 추천 `recommendations/{날짜}.json`(저녁은 `dinner/…`), 최근 선택 `latest/selection.json`, 생일 `birthdays/{서버}.json`, 게임 `games/{채널}.json`, 등급 `members/{서버}.json`(서버 주인은 대장), 저녁 추천 시각은 설정(평일 18:00).

1:1 스레드는 직장인 갑옷씨 이상만 쓰므로(§8), 스레드 주인에게는 물음 답하기·기억·가르치기를 모두 한다. 남의 스레드에 채팅한 다른 사람에게는 기억이 필요 없는 물음 답하기(1·2·4·5번)와 짧은 문맥까지만 한다 **[판단]**

### 6.2 읽고 답하는 방식 **[판단, 세부는 빌더]**

- **물음 읽기:** 물음말(뭐, 어디, 언제, 왜, 어때, 몇 …)과 화제말(점심, 저녁, 기분, 생일, 게임 …)로 의도마다 점수를 매겨 가장 높은 것을 고른다. 기준 점수를 못 넘으면 "모르는 물음"이다
- **문맥 이어받기:** 화제말 없이 짧게 물으면 직전 의도·대상(예: 방금 말한 식당)을 이어받는다. 자기 화제말이 분명하면 새 이야기다. "거기"처럼 가리키는 말은 직전 대상으로 푼다
- **짧은 문맥은 메모리에만:** 스레드마다 마지막 3마디(의도, 대상, 우사기가 되물은 것)를 메모리에 두고 10분 지나면 버린다. 저장하지 않는다. 봇을 다시 띄우면 사라진다
- **답 모양:** 지금처럼 우사기 소리 + 하치와레 번역이고, 소리 토막과 번역 토막은 한 짝씩이다. 답은 `NOTICES`처럼 (기분, 토막) 비트 틀로 만들고 `speak()`로 소리를 맞춘다. 틀마다 문장을 여럿 두어 되풀이를 줄인다
- **모르는 물음:** 아는 척하지 않고 하치와레가 "음… 잘 모르겠대. 무슨 뜻인지 알려 줄래?"라고 되묻는다 → §7. 가르치기를 못 하는 사람(§8 밖)에게는 "잘 모르겠대"까지만 한다
- 물음이 아닌 채팅(인사, 칭찬, 웃음 …)은 지금 `chat.py` 방식대로 답하되, 긴 기억이 있으면 가끔 그걸 꺼낸다 (예: 인사에 "3일 만이네!")

### 6.3 번역이 꺼져 있을 때 **[사용자: 지금 규칙대로]**

- 1:1 스레드 번역은 지금처럼 그 사람의 개인 설정을 따른다. 꺼져 있으면 우사기 소리만 나간다
- 그 사람은 안내·되물음·확인을 볼 수 없으므로, **번역이 꺼져 있는 동안(또는 하치와레 웹훅이 없을 때)은 기억을 읽지도 쓰지도 않고, 가르치기·되묻기도 하지 않는다** (모르게 저장하지 않도록) **[판단, 검토에서 나온 결과]**
- 다시 켜면 그때부터 이어서 쓴다 (안내를 아직 못 봤으면 안내부터)

### 6.4 긴 기억에 남기는 것 **[판단]**

암호화한 사람 파일 안(풀었을 때 JSON):

- 마지막으로 대화한 날
- 최근 기분 (날짜와 종류, 최근 10개까지. 새것이 들어오면 가장 오래된 것이 밀려남)
- 자주 하는 이야기 종류별 횟수 (`chat.py`의 종류)
- 좋아한다/싫어한다고 한 것 (정해 둔 말투 "~ 좋아", "~ 싫어"에서 뽑은 낱말, 최대 20개)
- 최근 이야기한 음식 (음식 낱말과 날짜, 최근 5개. "어제 라멘 먹었어?"에 씀)
- 가르친 것 (§7, 최대 50개)
- 기억 안내를 본 날

원문 문장은 넣지 않는다. 무엇을 남기는지는 §5.5 안내에 그대로 적는다. 시간이 지났다고 지우지는 않고(§3), 오래된 기분·음식은 "어제…" 같은 말에 쓰지 않을 뿐이다 (예: 7일 넘은 것은 꺼내지 않음).

## 7. 가르치기 (사용자가 이 흐름으로 하자고 함)

1. 모르는 물음이 오면 하치와레가 "음… 잘 모르겠대. 무슨 뜻인지 알려 줄래?"라고 되묻는다
2. 바로 다음 채팅이 설명("~라는 뜻이야", "~라고 하면 돼" 같은 말투)이면 기억한다. 몇 분 안에 안 오거나 설명처럼 보이지 않으면 평범한 채팅으로 다룬다 **[사용자, 몇 분은 판단: 5분]**
3. 두 가지로 받는다 **[사용자]**
   - **뜻 알려 주기:** "점메추는 점심 메뉴 추천이야" → 모르던 낱말을 이미 아는 의도에 잇는다. 다음부터 "점메추"에도 오늘 추천으로 답한다
   - **답 알려 주기:** "그럴 땐 '오늘도 화이팅'이라고 해 줘" → 다음에 비슷한 물음이 오면 하치와레가 그 말을 한다
4. 비슷한 물음인지는 낱말이 얼마나 겹치는지로 가린다 **[사용자]** (다듬은 낱말 집합의 겹침, 기준 0.5 **[판단]**)
5. 기억하면 "알았어! 다음엔 그렇게 말할게~"라고 확인한다 **[사용자]**
6. 알려 준 사람과 대화할 때만 쓰고, 그 사람의 키로 암호화해 저장하고, 본인이 보고 지울 수 있다 **[사용자]**
7. 알려 준 답 문장은 100자까지, 멘션은 알림 없이 글자로만 나간다(`allowed_mentions` 막음). 우사기 소리는 그 문장 토막 수만큼 만든다 **[판단]**

## 8. 누구의 기억인가

- **`/우사기`와 기억 기능(기억 쌓기·꺼내기, 가르치기, `/기억` 명령)은 같은 등급, 직장인 갑옷씨 이상**이다 **[사용자]**. 지금 `/우사기`는 누구나 쓰므로 `members.NEEDS`의 `우사기`를 0에서 직장인(WORKER)으로 올린다. 디스코드 서버 설정의 `/우사기` 역할은 사용자가 이미 직장인 이상으로 맞춰 두었다
- **직장인 아래가 되면 1:1 스레드에서 내보낸다** **[사용자]**. `/멤버강등`으로 직장인 아래가 되거나 `/멤버삭제`로 멤버가 아니게 되면, 그 사람에게 1:1 스레드가 있으면 그 스레드에서 내보낸다 (`DELETE /channels/{스레드}/thread-members/{사람}`. 봇이 만든 비공개 스레드라 봇이 내보낼 수 있음). 내보낸 것은 공개 답에 따로 알리지 않는다 (1:1을 썼는지 드러나지 않게) **[판단]**
- **강등되어도 기록은 지우지 않는다** **[사용자]**. 기억도, 스레드 기록(`threads/{서버}.json`)도 그대로 둔다. 다시 직장인 이상이 되어 `/우사기`를 쓰면 같은 스레드에 다시 넣고 기억을 이어서 쓴다 **[판단: 다시 넣기]**
- **이미 스레드가 있는 직장인 아래 사람:** 기능을 켤 때 지금 등급을 보고, 직장인 아래인 사람(행인, 멤버가 아닌 사람)은 1:1 스레드에서 내보낸다. 강등과 같은 규칙이다 **[판단]**
- 기억의 주인은 **그 1:1 스레드의 주인**이다 (`threads/{서버 id}.json`의 `usagi` 기록: 사용자 id → 스레드 id). 채팅한 사람이 그 스레드의 주인일 때만 기억을 읽고 쓴다 **[판단]**
- 다른 사람(스레드를 볼 수 있는 관리자 등)이 남의 스레드에 채팅하면 기억 없이 평범하게 답하고 아무것도 기록하지 않는다. 그 사람 자신의 기억도 쓰지 않는다 (남의 스레드에서 자기 기억이 보이면 안 되므로) **[판단]**
- 공개 우사기 채널에서는 누구의 기억도 쓰지 않는다 **[판단]**

## 9. 명령

- `/기억 보기` (**직장인 갑옷씨 이상**, 나만 보기): 우사기가 나에 대해 기억하는 것과 내가 가르친 것을 보여 준다 **[사용자]**
- `/기억 지우기` (**직장인 갑옷씨 이상**, 나만 보기): 전부 지우거나, 가르친 것 하나를 지운다. 전부 지우면 그 사람 파일을 없앤다 **[사용자]**
- `members.NEEDS`에 직장인(WORKER)으로 넣는다. 둘 다 같은 등급이라 맨 앞 명령 `/기억` 하나 아래에 둔다 (맨 앞 명령 하나 아래 같은 등급만 두는 규칙)
- `/우사기`도 직장인(WORKER)으로 올린다 (§8). `/도움`에 보이는 명령도 이에 맞게 바뀐다
- README의 서버 설정 권한 표에서 `/우사기`를 직장인 이상 줄로 옮기고, `/기억`을 직장인 이상으로 더한다. 사용자는 `/기억`의 역할을 서버 설정에서 직장인 이상으로 맞춰야 한다
- 기억 끄기 명령은 없다 (§3)

## 10. 나간 사람의 기록 지우기 **[사용자]**

- **언제:** 서버를 나갔을 때, 서버에서 추방됐을 때. 이 두 경우만 자동으로 지운다 (그 밖에는 본인의 `/기억 지우기`로만)
- **1:1 스레드도 지운다** **[사용자]**: 그 사람의 1:1 비공개 스레드를 디스코드에서 지운다 (`DELETE /channels/{스레드 id}`). 봇에 우사기 채널의 **스레드 관리**(MANAGE_THREADS, 1<<34) 권한이 있어야 한다. 봇은 자기에게 없는 권한을 스스로 줄 수 없어서 서버 주인이 서버 설정에서 켠다 (2026-10-26 확인: `daggle` 역할에 서버 전체로 켜져 있음). 권한이 없으면 스레드는 남기고 저장소 기록만 지우며, 시작할 때 로그로 알린다. 스레드가 이미 없으면(404) 넘어간다
- **무엇을:** 그 사람의 **사람별 기록 모두** — 우사기 기억(`memories/…`, 가르친 것 포함), 생일(`birthdays/{서버}.json`의 그 사람), 개인 번역 설정(`settings/hachiware_people.json`의 그 사람), 1:1 스레드 기록(`threads/{서버}.json`의 그 사람), 갑옷씨 등급(`members/{서버}.json`의 그 사람). 모두의 기록에 섞인 것(지난 투표 결과, 진행 중이거나 끝난 게임 점수 등)은 남긴다 **[사용자: "사람별 기록 모두", 남길 것의 경계는 판단]**
- **이미 나간 사람도:** 버튼 서버가 시작한 뒤 10분마다(구현 계획에서 정함), 지금 서버 사람 목록과 견주어 남아 있는 나간 사람의 기록을 찾아 지운다. 기억 파일은 이름이 해시라 지금 사람들의 해시를 만들어 견주고, 맞는 사람이 없는 파일을 지운다 **[판단]**
- **어떻게 알아채나:** `/추방`은 그 처리 안에서 바로 지운다. 스스로 나간 사람은 위의 10분마다 확인이 잡는다 (서버 사람 목록은 SERVER MEMBERS INTENT로 읽음 — 지금 켜져 있음). 처음에는 우사기 봇의 `on_member_remove`로 하려 했지만, 지우는 쓰기를 모두 버튼 서버의 처리 줄 안에 두어 겹쳐 쓰기를 없애려고 바꿨다 (구현 계획) **[판단]**
- **주의:** 생일·등급·스레드·번역 설정 파일은 버튼 서버도 쓴다. 우사기 봇이 지우는 순간 버튼 서버가 같은 파일을 고쳐 쓰면 한쪽이 사라질 수 있다 (두 프로세스라 버튼 서버의 처리 줄로는 못 막음). 어느 쪽이 지울지, 어떻게 겹치지 않게 할지 **[빌더]**
- 지운 것은 로그에 "몇 명의 기록을 지웠다" 정도만 남기고 이름·id는 남기지 않는다 **[판단]**
